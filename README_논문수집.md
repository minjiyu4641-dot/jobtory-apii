## 빠른 배치 수집 v4.3.3

짧은 시간 안에 현재 남은 요청 한도만 사용한 뒤 종료하려면 다음 명령을 사용합니다. 기존에 수집 중인 터미널에서는 먼저 Ctrl+C로 멈춘 후 실행합니다.

```powershell
python collect_papers.py --fast
```

- 요청 사이 기본 1초를 기다리며 순서대로 수집합니다. 병렬로 한도를 소진하지 않습니다.
- 실행 시작 때 이 프로젝트의 최근 1시간 사용량과 대기 기록을 확인합니다. **남은 요청 수와 180회 중 작은 값**이 이번 배치 상한입니다.
- 예를 들어 이미 177회를 사용했다면 최대 3회 요청으로 끝납니다. 계속 대기하면서 한도를 새로 채워 쓰는 모드는 아닙니다. 같은 명령을 즉시 다시 실행해도 시간당 기록은 유지됩니다.
- 검색과 논문별 상세조회가 각각 요청 1회입니다. 예를 들어 검색 1회 + 상세조회 10회는 요청 11회이며 논문 10편입니다. 저장 편수는 검색·중복·초록 제공에 따라 달라집니다.
- 배치 상한이나 제공처 제한에 도달하면 진행 기록을 남기고 종료합니다. 다음 실행은 미완료 페이지부터 재개하며 이미 저장한 ID는 건너뜁니다.
- `--fast --request-budget 50`처럼 더 작은 배치도 가능합니다. 빠른 배치의 요청 예산은 최대 180회입니다.
- 기본 명령 `python collect_papers.py`는 기존 20초 간격을 유지합니다.
- 최근 사용량 기록은 같은 PC·같은 프로젝트에서만 공유됩니다. 다른 서버나 PC의 사용량은 알 수 없어 제공처가 먼저 제한할 수 있으며, 제한 응답을 받으면 중단합니다. 수집할 동안 사이트의 API 보충은 잠시 꺼두고 DB로 질문하는 편이 관리하기 쉽습니다.


# Jobtory 논문 수집 추가 파일

2026-11-09 수정본: 사용자 인증키 화면의 **1시간 최대 200회 요청**에 맞춰 기본 요청 간격을 1초에서 **20초**로 변경했습니다. 트래픽 초과 시 진행 위치를 보존하고 재실행 대기 시간을 안내합니다. 기존 `data/paper_collection` 폴더를 그대로 유지하고 `collect_papers.py`와 `nal_collection.py`를 덮어쓰세요.

기존 Jobtory v4.2에서 검색어를 하나씩 순서대로 조회하고, 여러 페이지의 논문을 기존 Supabase `papers` 테이블에 누적합니다. 사이트 화면이나 기존 Python 파일은 교체하지 않습니다. 새 테이블이나 새 Supabase 프로젝트를 만들 필요도 없습니다.

## 1. 어디에 넣나요?

ZIP의 다음 네 파일을 현재 실행 중인 프로젝트의 **app.py와 같은 폴더**에 복사하세요. ZIP 안에 들어 있는 폴더 자체를 app.py 옆에 놓는 대신, 네 파일을 꺼내서 놓습니다.

- `collect_papers.py`: 터미널에서 실행할 파일
- `nal_collection.py`: 페이지 조회·중복 처리·진행 기록
- `nal_rate_limit.py`: 같은 프로젝트의 사이트와 공유하는 시간당 호출 기록
- `collect_keywords.json`: 5개 기업의 사업보고서에서 정리한 검색어 45개

그 폴더에는 기존 `paper_service.py`, `paper_repository.py`, `.env`도 있어야 합니다. 이 전체본에 포함된 파일을 사용합니다. v4.3에서는 사이트와 수집 파일이 시간당 호출 기록을 공유합니다. ZIP에는 API 키나 실제 논문 데이터가 들어 있지 않습니다.

## 2. VS Code에서 실행하기

기존 프로젝트 폴더를 VS Code로 열고, 새 터미널을 여세요. 사이트를 실행할 때 사용하던 Python 환경을 선택하세요.

필요한 패키지가 없다면 한 번 설치합니다.

```powershell
python -m pip install supabase python-dotenv
```

이미 연결을 확인한 기존 `.env`에서 다음 세 항목을 그대로 사용합니다. 키 값을 다른 곳에 공유하지 마세요.

```dotenv
SUPABASE_URL=기존_프로젝트_주소
SUPABASE_SECRET_KEY=기존_서버용_키
NAL_API_KEY=기존_국회도서관_API_키
```

검색어 목록만 확인하려면 다음 명령을 실행하세요. 이 명령은 API·DB를 호출하지 않습니다.

```powershell
python collect_papers.py --plan
```

실제로 수집하고 Supabase에 저장하려면 다음 명령입니다.

```powershell
python collect_papers.py
```

45개 검색어를 하나씩 처리합니다. 기본은 학술기사(ARTICLE), 검색어마다 1~3페이지, 한 페이지 최대 10건입니다. 검색 후보 상한은 45 × 3 × 10 = 1,350건입니다. 검색 결과가 적거나 중복되면 실제 저장 수는 더 적습니다. 연도나 초록 유무로 수집을 제한하지 않습니다.

## 3. 진행 상황은 어떻게 보나요?

터미널에 다음과 같이 표시됩니다. 아래 숫자는 설명용 예시입니다.

```text
DB에 이미 저장된 논문 5편 · 검색어 45개
[1/45] IT 아웃소싱 · 1/3페이지 조회
  검색 10건 · 이번 페이지 저장 8편 · 이번 실행 저장 누계 8편
```

마지막에는 저장 처리 건수, 그중 초록이 있는 건수, 기존 ID 건수, DOI 중복 건수, 빈 초록 보완 건수, API 요청 횟수를 표시합니다. **초록이 있다는 사실만으로 모든 논문이 AI 답변에 사용되는 것은 아닙니다.** 기존 사이트는 질문 관련성·연도·출처 등도 확인합니다.

실제 DB 건수는 Supabase의 Table Editor → `papers`에서 확인하세요. 사이트에서는 오른쪽 논문 활용 설정을 열어 **DB 논문 새로고침**을 누르세요. 기존 DB 읽기 연결을 그대로 사용합니다.

## 4. 멈추거나 오류가 났다면

`Ctrl+C`로 멈출 수 있습니다. 저장한 논문은 DB에 유지됩니다. 같은 명령을 다시 실행하면 마지막 미완료 페이지부터 다시 확인하고, 이미 저장한 논문 ID는 건너뜁니다.

```powershell
python collect_papers.py
```

인증·승인·통신·DB 저장 오류가 발생하면 멈추고 안내를 표시합니다. 오류를 검색 결과 0건으로 처리하지 않습니다. 원인을 해결한 다음 같은 명령을 다시 실행하세요.

요청 사이에 기본 **20초**를 기다립니다. 이 수집 파일만 계속 실행하면 시간당 약 180회 요청 수준입니다. 검색과 논문별 상세조회는 각각 요청 1회로 계산하므로 논문 수와 API 요청 수는 다릅니다. 같은 인증키를 쓰는 사이트나 다른 팀원의 요청은 이 파일이 합산해서 제어할 수 없습니다. 수집 중에는 같은 키로 다른 API 검색을 동시에 실행하지 않는 편이 좋습니다.

이번 실행의 검색+상세조회 요청이 2,000회에 도달하면 진행 위치를 유지한 채 일시 중지합니다. **2,000회는 실행 전체 예산이고, 공식 시간당 200회 한도와는 별개**입니다. 요청 간격 때문에 전체 수집은 여러 시간에 걸칠 수 있습니다.

트래픽 초과가 나면 대기 시각을 기록하고 종료합니다. 수정본으로 발생한 트래픽 초과 뒤에는 바로 재실행해도 1시간 동안 추가 요청을 보내지 않고 남은 대기 시간을 안내합니다. 제공처의 정확한 초기화 방식·시각은 확인되지 않아 1시간 후 해제를 보장하지 않습니다. 계속 제한되면 더 기다리거나 제공처에 문의하세요. **기존 버전에서 방금 트래픽 초과가 났다면, 그 오류 시점부터 최소 1시간을 기다린 후 수정본을 실행**하세요.

파일을 바꾸기 전에도 기존 코드에서 아래 명령으로 요청 간격을 늘릴 수 있습니다. 이 경우에도 한도가 회복된 뒤 실행해야 합니다.

```powershell
python collect_papers.py --interval 20
```

승인된 이용 조건과 제공처가 안내한 호출 한도를 따라 사용하세요.

## 5. 범위 조절하기

특정 검색어만 수집할 수 있습니다. 한 번씩 별도 실행해도 같은 `papers` 테이블에 누적됩니다.

```powershell
python collect_papers.py --query "스마트팩토리"
python collect_papers.py --query "전기차 충전"
```

각 검색어의 10페이지까지 확장하려면 다음과 같습니다. 기존에 3페이지까지 끝난 검색어는 4페이지부터 이어집니다. 이미 결과 끝에 도달한 검색어는 건너뜁니다.

```powershell
python collect_papers.py --pages 10
```

같은 검색어로 신규 자료를 다시 확인하려면 진행 위치를 초기화해 처음부터 검색하세요. DB 자료를 삭제하지 않습니다. 기존 ID는 건너뛰므로 기존 ID의 상세정보를 전부 갱신하는 명령은 아닙니다.

```powershell
python collect_papers.py --reset-progress
```

학위논문 수집은 해당 API 활용 승인이 있는 경우 다음 명령으로 실행합니다. 학술기사와 별도 ID·진행 위치로 관리합니다. 현재 사이트의 자동 논문 선택은 자료유형도 확인하므로, 학위논문을 쓰려면 사이트의 자료유형 설정도 맞춰야 합니다.

```powershell
python collect_papers.py --type THESIS
```

`collect_keywords.json`의 `queries` 배열에 검색어를 추가할 수도 있습니다. 같은 검색어가 여러 그룹에 있으면 한 번만 검색합니다. 기업 표시는 수집 후보의 연결 정보이며, 해당 기업이 논문의 기술을 직접 개발했다는 뜻이 아닙니다.

## 저장 방식과 현재 범위

- **DB**: 기존 `papers`의 동일 논문 ID는 중복 저장하지 않습니다. 새로 수집한 자료의 유효한 DOI가 기존 자료와 같으면 기존 논문에 연결하고 별도 행을 추가하지 않습니다. 기존의 빈 초록을 새로 받은 실제 초록으로 보완할 수 있습니다. 과거에 이미 DB에 들어간 중복 행을 삭제하지는 않습니다. DOI가 없거나 다르게 기재된 같은 논문은 중복으로 남을 수 있습니다.
- **내용**: 제공된 제목·저자·학술지·연도·초록·DOI·링크·주제어 등입니다. 초록을 지어내거나 원문 PDF를 내려받지 않습니다. API가 제공하는 정보와 해당 이용·권리 조건 범위에서 사용하세요.
- **수집 기록**: `data/paper_collection/progress.json`에 진행 위치, `last_run.json`에 최근 집계, `papers_backup.jsonl`에 조회한 원본 필드, `matches.jsonl`에 검색어·기업 연결 후보를 기록합니다. 중단 후 재실행하면 로컬 JSONL 기록에 같은 항목이 반복될 수 있습니다. DB 중복 처리와 별개입니다. 키 값은 기록하지 않습니다.
- **검색어 연결**: 기업·검색어의 모든 연결 이력은 로컬 `matches.jsonl`에 남습니다. 기존 DB의 `query` 필드는 대표 검색어 한 개이며, 여러 검색어를 저장하는 새 테이블을 만들지는 않습니다.
- **사이트**: 현재 v4.2는 DB에서 최대 2,000편을 불러오는 방식입니다. 그 이상을 저장해도 DB에는 남지만, 사이트에서 전체를 활용하려면 DB 검색 기능을 확장해야 합니다.
- **LLM**: 수집 단계에서는 OpenAI를 호출하지 않으며 OpenAI 키가 필요하지 않습니다.

데이터 출처: 국가학술정보 Open API 데이터(국회도서관).

공식 안내: https://losi-open.nanet.go.kr/user/information.do
